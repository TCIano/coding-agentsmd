# AI 项目维护文档系统：框架 v0.3.0

状态：2026-10-26 已确认，后续可修订。本文描述系统约定；当前实现与尚未实现的部分见「工具边界」。

## 用途与边界

系统服务于采用 Git 的新项目，以及多人和多个 AI 工具的长期协作。项目文档与代码一起保存版本。系统提供初始化、检查、快照、现有文档检查和模板升级能力。工具检查可确定的格式和关联关系，实际内容由任务执行者和合并负责人判断。

每个接入项目从同一套带版本的模板创建文档，并记录采用的模板版本。这个系统的仓库维护模板和检查工具。项目可增加正式文档类型，但须同时提供模板、存放位置和基本检查规则。

## 模板放置位置

这套系统仓库的 `templates/` 保存带版本的系统模板：

```text
templates/
  project/                初始化时使用的 README.md、AGENTS.md、CONTEXT.md 和 docs/ 基础文件
  documents/              需求、缺陷、接口、设计决定、任务变更记录及两种快照的文档模板
```

初始化一个项目时，工具把基础文件放到该项目根目录，同时把本次采用的文档模板复制到该项目的 `docs/_templates/`，形成项目模板副本，并在 `docs/system.yml` 记录模板版本。以后新建文档时，从项目自己的 `docs/_templates/` 生成；升级时与系统模板的新版本比较。这样项目离开这套工具也能看到自己正在使用的模板。

当前可运行的入口是 `scripts/init_project.py`（初始化）、`scripts/check_task.py`（检查全部文档或某个任务）和 `scripts/upgrade_templates.py`（查看模板升级差异），用法见根目录 `README.md`。快照生成尚未实现，完整缺口见「工具边界」。

## 接入项目的最小结构

```text
README.md                 项目用途、运行方式和入口
AGENTS.md                 人与 AI 的协作规则、文档检查规则
CONTEXT.md                项目特有术语；不写实现细节
docs/
  index.md                当前正式文档的索引
  requirements/           需求
  bugs/                   功能、数据、安全、性能缺陷
  interfaces/             对外或跨模块的接口说明
  adr/                    难以逆转且需解释取舍的设计决定
  tasks/                  每个任务的任务变更记录和工作接续快照
  snapshots/              项目状态快照
  attachments/            正式文档引用的图片等附件
  _templates/             项目模板副本
  modules/                项目自行增加的模块文档，可选
  CHANGELOG.md            发布时汇集的项目变更记录
  document-map.yml        代码文档对应表（代码区域与相关文档的粗粒度对应）
  system.yml              项目采用的模板版本及检查设置
```

初始化时创建上述入口、目录、配置和各类型的起始草稿。起始草稿明确标为“草稿／待填写”，不能被索引为现行文档；填写实际内容、分配编号并审核后才转为现行。临时调查材料可放在任务目录的 `drafts/`，不能被当作当前规范引用。附件由正式文档引用，不能单独代替说明。项目可以增设目录；如果它属于正式文档类型，还要为它声明模板和检查规则。

## 模板的最小内容

| 类型 | 必填内容 |
| --- | --- |
| 需求 | 要解决的问题、适用范围、验收方式、负责人、状态、关联任务 |
| 缺陷 | 复现条件、预期与实际行为、影响、修复说明、回归验证、处理状态 |
| 接口 | 使用方、输入输出、错误情况、兼容性、示例、验证时间 |
| 设计决定 | 背景、决定、取舍原因；只有确有价值时才补充备选方案与后果 |
| 任务变更记录 | 任务编号、改动和原因、关联资料、文档影响判断、验证结果 |
| 工作接续快照 | 当前进度、已验证、未完成、下一步、代码版本和工作区状态 |
| 项目状态快照 | 对应代码版本、生成与验证时间、功能和结构、已知问题、未验证部分 |
| 项目变更记录 | 发布版本、汇集的任务变化、重要兼容性变化和人工审阅结果 |

每份正式文档还要有文档 id（`id`）、类型（`type`）、标题（`title`）、文档状态（`document_status`）、负责人（`owner`）和最近更新时间（`updated_at`）这 6 个通用字段；文档 id 是文档的标识，任务编号是任务的标识，引用任务时写入 `related_tasks`。不同类型可以在共同字段之外增加自己的字段。起始草稿不表示项目实际存在一项需求、缺陷或设计决定。

### 类型标识与模板

中文类型名、frontmatter 的 `type` 值和模板文件必须一一对应；下表列出当前对应关系，模板 frontmatter 和检查脚本的 `type` 值都应与 `scripts/doc_types.py` 一致。项目自定义类型不在表中，须在项目内声明模板、存放位置和检查规则（当前工具只给警告）。

| 中文类型名 | `type` 值 | 模板文件 |
| --- | --- | --- |
| 需求 | `requirement` | `templates/documents/requirement.md` |
| 缺陷 | `bug` | `templates/documents/bug.md` |
| 接口 | `interface` | `templates/documents/interface.md` |
| 设计决定 | `adr` | `templates/documents/adr.md` |
| 任务变更记录 | `task-change` | `templates/documents/task-change.md` |
| 工作接续快照 | `work-snapshot` | `templates/documents/work-snapshot.md` |
| 项目状态快照 | `project-snapshot` | `templates/documents/project-snapshot.md` |
| 项目变更记录 | `project-changelog` | `templates/project/docs/CHANGELOG.md` |

这张表以 `scripts/doc_types.py` 为准，契约测试锁死。新增或修改类型要同步三处：`scripts/doc_types.py`、模板文件（按表中路径）和这张表；两个脚本不用改。

项目变更记录目前由项目基础文件提供，不在 `docs/_templates/` 中；初始化时写入 `docs/CHANGELOG.md`。

### 任务变更记录的表头

`templates/documents/task-change.md` 的「文档影响判断」和「验证」表头是检查器的硬契约。必须原样使用以下列名，不能缩短、改名或缺少列；列顺序可以不同，检查器只忽略空格和加粗标记：

- 「文档影响判断」：`文档类型或具体文件`、`结论（已更新／检查后无需更新）`、`链接或无需更新的理由`。
- 「验证」：`命令或操作`、`结果`、`代码版本`、`时间`、`未运行原因与影响`。

表头不符时，检查器报错并列出缺失列和实际表头，不按列下标猜。

## 文档状态与可追溯性

正式文档标记为“草稿、现行、已取代、已归档”之一。只有现行文档能直接说明项目当前约定；已取代文档必须指向接替文档。缺陷另有处理状态，不能用文档状态代替。历史快照保留当时的时间和代码版本，不会因为被归档而失去历史价值。

本系统仓库的框架文档和 ADR 用「已确认」「已接受」表示评审结论，不属于接入项目的 `document_status` 四态；接入项目的正式文档仍只用草稿、现行、已取代、已归档。

每项工作有项目内唯一的任务编号，可关联外部 issue。需求、缺陷、任务变更记录、验证结果和快照通过该编号互相引用。任务变更记录写清改动、原因、文档影响判断、验证结果和关联材料。执行者对每类受影响文档写“已更新”或“检查后无需更新”；后一种情况必须说明原因，合并负责人确认。

功能、数据、安全和性能缺陷必须有缺陷文件，记录复现条件、预期与实际行为、原因、修复和回归验证。纯文案或排版修正可只写任务变更记录，但仍需任务编号与验证结果。

## 两种快照

工作接续快照属于任务：记录当前进度、已验证事项、未完成事项、下一步、所依据的代码版本及未提交改动。中断或交接时更新；任务结束后标明结束并保留在 Git 中。

项目状态快照属于项目：在发布版本、主要功能交付、架构或外部接口发生重要变化时保存。它记录当时的功能、结构、已知问题、所依据的代码版本、生成时间、验证时间和未验证部分。普通修复无需新建项目状态快照。

快照只记录复现所需的非敏感信息。凭据和个人数据只写安全获取方式或存放位置，不写具体值。检查工具扫描常见泄露形式。

“代码版本”指快照所描述和验证的代码版本，不要求快照文件写入它自身的 Git 提交号。工具应区分已提交版本与带未提交改动的工作区，避免把两者混称为同一状态。

## 一次任务的流程

1. 建立任务编号，关联需求或缺陷，读取 `README.md`、`AGENTS.md`、`CONTEXT.md` 和相关现行文档。
2. 修改代码和测试。依据 `document-map.yml` 的模块级规则，提示可能受影响的文档；全新模块由执行者补充模块级规则，合并负责人核实。无需逐个代码文件登记。
3. 更新必要的正式文档及任务变更记录；对无需更新的类型写理由。记录运行的验证、结果和代码版本；未运行的验证写原因和影响。未完成必要验证时，由项目维护者结合影响决定是否合并，并留下后续验证任务。
4. 中断或交接时更新工作接续快照。遇到文档与代码、测试或决定冲突，标记“待核实”，记录位置、发现时间和负责人。相关冲突须在合并前解决；无关冲突留下后续任务。
5. 本地运行检查。合并请求使用同一检查命令，合并负责人核实内容、理由与必要链接。有远程仓库的团队项目保护主分支。允许直接提交的项目也运行本地检查，但本地检查可以被跳过。
6. 重要节点创建项目状态快照。发布时工具从已合并的任务变更记录汇集 `CHANGELOG.md`，由人审阅。具体汇集算法留待实现时确定。

## 工具边界

首版计划提供五类操作：初始化项目文档、检查当前任务、制作快照、检查现有文档、升级模板。共同检查命令可从本地或合并检查调用，不绑定某个 Git 平台。

检查工具可以验证模板字段、任务编号、引用目标、文档状态、代码版本信息、模板版本、必要的任务变更记录，以及代码文档对应表中的代码区域到文档的对应关系。它提示可能遗漏的文档，不声称能证明描述与代码的语义一致。执行者负责判断内容，合并负责人负责确认。缺少必要任务变更记录、相关文档冲突未处理等问题须先处理；验证因环境限制未完成时允许项目维护者记录原因和影响后作决定，不能只靠工具的一条失败提示代替判断。

不同 AI 工具以 `AGENTS.md` 和 `docs/` 为共同依据。系统按需生成只指向 `AGENTS.md` 的工具专用入口文件，项目仅启用实际使用的工具。工具专用入口不复制长期规则。

当前实现（0.3.0）：`scripts/init_project.py` 初始化项目；`scripts/check_task.py <项目> [任务号]` 只读检查正式文档：不带任务号时检查全部正式文档的必填字段、空串、文档状态、本地链接、重复 id、类型和 `document-map.yml`，并提示模板版本差异；带任务号时在此基础上检查该任务的任务变更记录、文档影响判断表、验证表和合并检查小节。发现错误退出 1，环境或用法错误退出 2，版本较旧只警告；`scripts/upgrade_templates.py <项目> [--check]` 只读展示项目 `docs/_templates/` 与系统模板的差异，不覆盖项目内容，`--check` 在有差异或缺失时退出 1，版本较旧本身不构成失败。

尚未实现或仅部分实现的项：

- 快照生成。
- 快照类字段校验（`generated_at`、`verified_at`、`code_revision`、`task_status`）。
- 按类型的正文必填内容；当前只校验任务变更记录的四个小节。
- 敏感信息扫描。
- 发布时从已合并的任务变更记录汇集 `CHANGELOG.md`；汇集算法未定。
- AI 工具专用入口文件生成。
- 已提交版本与带未提交改动的工作区区分。
- 依据代码改动区域提示可能受影响的文档；当前只校验代码文档对应表中登记的文档是否存在。
- 自定义文档类型的模板、存放位置和检查规则声明；当前只给警告。
- 合并检查内容确认（合并负责人、相关文档冲突是否解决）；当前只提示小节为空。

## 模板版本

系统仓库为模板和检查规则使用同一个版本号。接入项目在 `docs/system.yml` 记录所采用版本。升级工具展示系统模板与项目模板副本的差异，并单独列出项目自定义模板，不直接覆盖项目写过的内容。项目可暂留旧版，但检查结果应提示当前版本与可用版本的差异，不单因版本较旧而失败。

### 0.2.0 迁移影响

0.2.0 收紧了任务检查，既有接入项目在升级前需要核对：

1. 任务变更记录的「文档影响判断」和「验证」表必须使用模板的表头列名；表头缺失、缩短或改名会报错（只忽略空格和加粗标记）。
2. `id`、`type`、`title`、`document_status`、`owner`、`updated_at` 六个通用字段不能为空字符串；空串现在算错误。
3. 「文档影响判断」的结论只接受「已更新」或「检查后无需更新」；写「需要更新」会被判错。
4. 核对后把 `docs/system.yml` 的 `system_version` 更新为 `0.2.0`；项目模板副本有差异时先用 `scripts/upgrade_templates.py` 查看并人工合并。

另外，项目变更记录模板补充了 `id` 字段；既有项目可自行补上，不影响当前检查。

检查器的变化只影响检查结果，不改写项目文件；模板变化只影响之后新初始化的项目。

### 0.3.0 迁移影响

0.3.0 增加全量检查，并收紧了扫描规则：

1. `scripts/check_task.py <项目>` 不带任务号时执行全量检查：正式文档的必填字段、空串、本地链接、文档状态、重复 id、类型和 `document-map.yml`；带任务号时保留任务记录检查。
2. 正式文档缺少 frontmatter 会报错；起始草稿和模板副本仍按原有规则跳过，`docs/index.md` 作为索引页显式豁免。
3. 字段和链接检查现在覆盖全部正式文档，不再只查任务相关文档。
4. 升级前先跑一遍全量检查，清掉上述问题，再把 `docs/system.yml` 的 `system_version` 更新为 `0.3.0`。

全量检查只读，不改写项目文件。

## 场景检查：修复登录缺陷并修改接口

1. 执行者创建任务编号，并建立缺陷文件，写下登录失败的复现条件、影响和预期行为。
2. 修改登录代码和公开接口。代码文档对应表提示登录模块的接口文档；执行者更新它，并在任务变更记录里解释其他文档为何无需更新。
3. 执行者记录测试结果。如果集成环境不可用，写明哪些测试没跑、可能影响什么，并留下后续验证任务；项目维护者决定是否允许合并。
4. 中途换人或换 AI 时，更新工作接续快照。合并负责人检查缺陷、接口文档、任务变更记录、验证和文档影响判断。
5. 接口有重要变化，因此保存项目状态快照。发布时汇集该任务变更记录到 `CHANGELOG.md`，由人审阅。
